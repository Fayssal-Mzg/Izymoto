# Rapport — lot 2.1 « pool des chauffeurs sans données personnelles » (SENSIBLE)

Date : 2026-10-14 · Branche : `lot/2.1-pool-serveur` (depuis `main` e843113) · Cadrage : `docs/plans/2026-10-13-lot-M2-prerequis-serveur.md` (M2a) · Décisions : D-014 (clôt D-010), D-015.

## Résultat
- `ridePool/{bookingId}` : écrit uniquement par le serveur, lu par les chauffeurs validés **en service**. Il contient la zone (pôle, arrondissement de Paris ou département, d'après une table fermée), la date, la distance, le prix, la part du chauffeur et la priorité. Il ne contient aucun nom, téléphone, e-mail, note ou adresse exacte.
- Les actions du chauffeur passent par `POST /api/rides/{accept|start|complete|release}`, et celles de l'admin par `POST /api/admin/booking` : transaction, jeton vérifié, journal `auditLogs`.
- D-003 est vérifié sur le compte et sur le téléphone.
- Admin :
  - une empreinte active se libère par « Annuler le hold » ;
  - une course déjà payée ne s'annule qu'après confirmation du remboursement ;
  - une course au paiement actif ne peut pas être supprimée.
- Synchronisation du pool dans la transaction de création : carte, carte enregistrée, portefeuille et entreprise, hybride (perso et entreprise). Le webhook et l'abandon d'empreinte la déclenchent aussi. Une réconciliation quotidienne sert de filet de sécurité.
- Coordonnées du passager : le chauffeur ne les lit que **pendant la course** (règle `bookings`). Son historique est `driverRides/{uid}/rides` : zones, date, statut, gains.
- Règles : plus aucune écriture chauffeur dans `bookings`, ni lecture du pool dans `bookings`. Le client chauffeur web est branché sur `ridePool` et sur les routes serveur.

## Réserves
- D-003 : le moyen de paiement n'est pas comparé, et le téléphone de la réservation est saisi par le passager. Décision de Fayssal attendue : lot dédié (empreinte de carte Stripe) ou écart acté.
- Pas de limitation de débit ni d'App Check sur `/api/rides/*` : un script pourrait accepter les courses avant les autres chauffeurs. À planifier.
- `bookingId` (identifiant Stripe) visible dans `ridePool` : c'est l'identifiant du document, nécessaire à l'acceptation, et il est inexploitable sans clé secrète.
- Front chauffeur et admin non testés par composant (forme des requêtes vérifiée sur l'émulateur).

## Procédure de déploiement (ordre obligatoire)
1. **Index d'abord**, sans effet sur l'existant : `npx firebase deploy --only firestore:indexes --project <projet>`. Attendre l'état « Activé » pour l'index `bookings` (driverId, status, createdAt).
2. **Code** : fusion de la PR, puis attendre que Vercel soit Ready.
3. **Réconciliation manuelle, pool et historique seulement**, sans toucher aux empreintes :
   `curl -H "Authorization: Bearer <CRON_SECRET>" "https://<site>/api/cron/deferred-holds?mode=pool&backfill=1"`
4. **Règles** : `npx firebase deploy --only firestore:rules --project <projet>`, aussitôt après l'étape 3. Entre les étapes 2 et 4, les chauffeurs voient un pool et un historique vides : choisir un moment calme.
5. **Vérification** avec un compte chauffeur en service : la course apparaît par zone, l'acceptation fonctionne, puis l'adresse et le téléphone s'affichent, et l'historique reste visible.
